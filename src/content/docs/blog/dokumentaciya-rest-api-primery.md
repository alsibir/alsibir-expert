Документация REST API должна отвечать на практические вопросы разработчика: куда отправить запрос, какие данные передать, что вернётся в ответ и как действовать при ошибке. Одного списка URL и методов HTTP недостаточно.

Ниже приведён минимальный набор разделов, образец описания операции и способы поддерживать документацию в актуальном состоянии. Подход подходит и для Markdown, и для корпоративного документа в Google Docs или Word.

## Что включить в документацию API

В начале документа следует указать назначение интерфейса, базовый адрес, поддерживаемые версии, формат обмена, способ аутентификации и общие правила обработки ошибок.

Для каждой операции необходимо описать:

1. Назначение действия.
2. HTTP-метод и относительный путь.
3. Требуемые права или способ аутентификации.
4. Параметры пути, строки запроса, заголовки и тело запроса.
5. Ограничения и правила проверки входных значений.
6. Успешные ответы и возможные ошибки.
7. Готовые примеры запросов и ответов.

Дополнительно полезны сведения о пагинации, сортировке, фильтрации, ограничениях частоты вызовов и совместимости версий. Эти разделы добавляются тогда, когда соответствующее поведение действительно предусмотрено интерфейсом.

## Пример описания метода REST API

Рассмотрим **условный сервис задач**. Примеры ниже демонстрируют оформление документации, а не контракт действующего программного продукта.

### Получение задачи по идентификатору

| Поле | Значение |
| --- | --- |
| Назначение | Вернуть сведения об одной задаче |
| HTTP-метод | `GET` |
| Путь | `/api/v1/tasks/{task_id}` |
| Авторизация | Токен в заголовке `Authorization` |
| Формат ответа | `application/json` |

Параметр пути:

| Параметр | Тип | Обязательность | Описание |
| --- | --- | --- | --- |
| `task_id` | Строка | Да | Уникальный идентификатор задачи |

Пример запроса:

```http
GET /api/v1/tasks/42 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer <access_token>
```

Пример успешного ответа:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": "42",
  "title": "Подготовить руководство пользователя",
  "status": "in_progress"
}
```

Примеры ошибок:

| Код | Когда возвращается |
| --- | --- |
| `400` | Неверный формат входного идентификатора |
| `401` | Отсутствует или недействителен токен |
| `403` | Пользователь не имеет права читать задачу |
| `404` | Задача не найдена |
| `500` | Непредвиденная ошибка сервера |

Нужно отдельно описать **фактический формат тела ошибки**. Например:

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Задача не найдена"
  }
}
```

Приведённые коды — демонстрационный пример. Реальный API может иначе разграничивать состояния `403` и `404`, а также использовать другую структуру ошибок. Это следует согласовать с разработчиком и проверить тестовым запросом.

## Что делать, если документацию требуют вести в Google Docs

Формат хранения не определяет качество содержания. Для документа в Google Docs рекомендуется создать единый шаблон операции с полями «назначение», «метод», «адрес», «параметры», «запрос», «ответ», «ошибки», «примечания» и «версия».

При большом количестве методов ручное копирование создаёт риск расхождений. В таком случае пригоден следующий процесс:

1. Разработчики поддерживают машиночитаемый контракт API.
2. На его основе создаётся технический справочник или проверяемая выгрузка.
3. Необходимые разделы экспортируются в согласованный формат.
4. Технический писатель добавляет сценарии работы, пояснения и ограничения.
5. Перед выпуском документа выполняется сверка с тестовым экземпляром сервиса.

Если машиночитаемого контракта нет, следует хотя бы вести реестр методов и проверять примеры запросов при каждом изменении интерфейса.

## Для чего нужен OpenAPI

[OpenAPI](https://www.openapis.org/) — спецификация для формального описания HTTP API. Она помогает определить операции, параметры, схемы данных и варианты ответа в формате YAML или JSON. Swagger UI, Swagger Editor и другие инструменты могут использовать такой контракт, но **OpenAPI и Swagger — не одно и то же**.

Упрощённый пример файла OpenAPI:

```yaml
openapi: 3.1.0
info:
  title: Example Tasks API
  version: 1.0.0
servers:
  - url: https://api.example.com
paths:
  /api/v1/tasks/{task_id}:
    get:
      summary: Получить задачу
      parameters:
        - name: task_id
          in: path
          required: true
          schema:
            type: string
      responses:
        '200':
          description: Задача получена
        '404':
          description: Задача не найдена
```

Это демонстрационный фрагмент, а не полная спецификация: в рабочем варианте требуется указать схемы данных, безопасность, все поддерживаемые ответы и ограничения. Важно зафиксировать согласованную версию OpenAPI в проекте.

## Как исключить ошибки в документации API

**Документировать следует наблюдаемое поведение, а не только желаемое.** Для каждого метода нужно проверить запросы на тестовом стенде и удостовериться в соответствии типов данных, кодов ответа и правил авторизации.

Наиболее частые ошибки:

- Указан `POST`, хотя сервис принимает `PUT` или `PATCH`.
- Поле помечено необязательным, но сервер отклоняет запрос без него.
- В примерах используется устаревший адрес или версия API.
- Не описаны ответы для отсутствующих прав доступа.
- Примеры JSON не проходят синтаксическую проверку.
- Изменение интерфейса выпущено без обновления спецификации.

## Краткий чек-лист для публикации

Проверить: назначение API, базовый URL, версию, авторизацию, все публичные операции, обязательные параметры, тела запросов, форматы ответов, ошибки, реальные примеры и дату актуализации. Для интеграций дополнительно нужны тайм-ауты, повторные запросы и правила обработки ограничений — если они определены договором интерфейса.

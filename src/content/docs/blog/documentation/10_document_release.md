**Направление:** техническое документирование, инструменты разработки · **Актуализация:** 09.10.2026.

Комплект документации является результатом производственного процесса: исходники меняются, графические материалы пересобираются, ссылки обновляются, документы проходят проверку и выпускаются для определенной версии продукта. Если релиз не воспроизводим, невозможно надежно установить, какие именно файлы были приняты заказчиком.

## 1. Три разных сущности: исходник, результат и поставка

**Исходник** — редактируемый материал: `.docx`, `.md`, `.puml`, `.drawio`. **Производный файл** — публикационная форма: `.pdf`, `.html`, `.svg`. **Поставка** — утвержденная совокупность файлов с реестром, версиями и контрольными суммами. Эти понятия не следует смешивать.

```text
project-docs/
  sources/
    tz/
    pmi/
    guides/
  diagrams/
    architecture.puml
  assets/
  checks/
    issues.md
    release-checklist.md
  release/
    1.0.0/
      documents/
      manifest.csv
      sha256sum.txt
  README.md
```

Структура демонстрационная. В реальном проекте ее следует согласовать с требованиями к именованию, электронному архиву и исходной системе управления документами.

## 2. Правила именования

Имя должно помогать человеку найти документ и не должно конфликтовать с файловыми системами. Рекомендуется единая схема, например:

```text
DEMO_TZ_1.0.0_r03.docx
DEMO_PMI_1.0.0_r05.docx
DEMO_ADMIN_GUIDE_1.0.0_r02.docx
```

Здесь `1.0.0` обозначает версию продукта, а `r03` — редакцию документа. Это разные величины. В документе необходимо отдельно фиксировать его нормативное **обозначение**, которое может не совпадать с именем файла. По одному имени нельзя автоматически устанавливать его юридический статус.

В Windows и Linux ограничения по **длине компонента имени** и по **длине полного пути** могут различаться. Для переносимого архива нужен консервативный контроль обоих параметров и проверка Unicode/UTF-8. Универсального одинакового для всех файловых систем предела полного пути нет.

## 3. Git и управление изменениями

Git полезен для текстовых исходников, схем и метаданных; бинарные документы Word и PDF также можно хранить, но удобство сравнения ограничено. Для крупных бинарных файлов может потребоваться Git LFS или специализированная система управления документами.

Вариант процедуры выпуска:

```bash
git status
git add sources diagrams checks
git commit -m "docs: update release 1.0.0"
git tag -a docs-1.0.0-r03 -m "Documentation release 1.0.0 revision 03"
```

Перед созданием тега требуется проверить, что в индекс не попали секреты, лишние временные файлы, персональные данные и служебные токены. История Git **не удаляет автоматически** ранее зафиксированные секреты; их публикация требует отдельного реагирования.

## 4. Манифест поставки

Для каждого файла указываются обозначение, наименование, версия, формат, контрольная сумма и результат контроля:

| Имя файла | Обозначение | Версия продукта | Редакция документа | Статус |
|---|---|---|---|---|
| `DEMO_TZ_1.0.0_r03.pdf` | `DEMO-ТЗ` | 1.0.0 | 03 | Проверен |
| `DEMO_PMI_1.0.0_r05.pdf` | `DEMO-ПМИ` | 1.0.0 | 05 | Проверен |

**Пример проверки SHA-256 в Linux:**

```bash
cd release/1.0.0/documents
sha256sum -- *.pdf > ../sha256sum.txt
cd ..
sha256sum -c sha256sum.txt
```

Контрольная сумма подтверждает совпадение содержимого с зафиксированным значением, но **сама по себе не подтверждает автора или доверенность источника**. Для доказательства происхождения нужны согласованные процедуры подписания/передачи.

## 5. Синхронизация и резервное копирование — разные задачи

Двусторонняя синхронизация обеспечивает согласование изменений между двумя местами. Ошибочное удаление или повреждение может быть распространено на обе стороны. Односторонняя копия без версионирования также может перезаписать исправный материал поврежденным.

Для устойчивой стратегии требуются: отдельная версия резервных копий, политика хранения, контроль ошибок, периодическая пробная процедура восстановления и защита хотя бы одного экземпляра от случайного изменения основным процессом синхронизации.

**Демонстрационная модель:** рабочий каталог → ежедневная версия на отдельном носителе → независимая еженедельная архивная копия. Между этапами проводится проверка результатов, а не предполагается их успешность по факту запуска программы.

## 6. Воспроизводимость сборки

Процедура должна отвечать на вопросы:

1. Какая редакция исходников взята?
2. Какая версия генератора диаграмм и конвертера документов использована?
3. Какие шрифты и настройки форматирования применялись?
4. Где хранятся результаты автоматических проверок?
5. Кто разрешил выпуск и какой набор файлов вошел в поставку?

Простой файл `release-notes.md` фиксирует состав изменений и ограничения. Манифест с контрольными суммами обеспечивает проверку целостности. Отчет о проверке позволяет определить, что именно считалось завершенным на момент выпуска.

## 7. Контрольный перечень релиза

- Зафиксированы версии ПО и документов, а также идентификатор исходной редакции.
- В исходниках отсутствуют временные метки исправлений и неподтвержденные значения.
- Подписи, ссылки, нумерация и оглавления обновлены и проверены в итоговых файлах.
- Все файлы манифеста существуют, их контрольные суммы совпадают.
- Доступность и читаемость архивов проверены на целевой ОС.
- Наличие исходников, конечных форматов и протокола приемки подтверждено.
- Процедура восстановления проверена на отдельном тестовом месте.

## Вывод

Воспроизводимый документационный релиз — результат дисциплины управления изменениями, контролем качества, конфигурацией и резервированием. При таком подходе комплект остается проверяемым после передачи и пригоден для безопасного сопровождения следующей редакции продукта.

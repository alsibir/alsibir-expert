Для подключения к Linux-серверу по SSH можно использовать пару ключей вместо постоянного ввода пароля учётной записи. Закрытый ключ остаётся на компьютере пользователя, а открытый записывается на сервер. После настройки сервер проверяет владение закрытым ключом, не получая сам закрытый ключ.

В этой инструкции рассматривается современный OpenSSH и алгоритм Ed25519. Действия подходят для Linux и актуальных версий Windows с установленным клиентом OpenSSH.

## Что потребуется

- Действующая учётная запись на сервере и возможность подключиться к ней.
- Адрес или имя сервера.
- Клиент OpenSSH на компьютере.
- Доступ для добавления открытого ключа в домашний каталог пользователя на сервере.

**Важно:** закрытый ключ нельзя отправлять на сервер, публиковать в Git, прикладывать к письму или передавать другим пользователям. Файл с расширением `.pub` — открытая часть пары.

## Шаг 1. Проверить существующие ключи

В терминале Linux выполнить:

```bash
ls -la ~/.ssh
```

В PowerShell Windows:

```powershell
Get-ChildItem "$env:USERPROFILE\.ssh" -ErrorAction SilentlyContinue
```

Если ключи уже есть, не следует перезаписывать их без необходимости. Для нового сервера или проекта можно создать отдельную пару с собственным именем.

## Шаг 2. Создать ключ Ed25519

В Linux, Windows PowerShell или Windows Terminal выполнить:

```bash
ssh-keygen -t ed25519 -C "server-access"
```

При запросе имени файла допускается оставить предложенный путь (`~/.ssh/id_ed25519`) либо задать другой, если ключ с таким именем уже существует. Желательно установить надёжную парольную фразу для защиты закрытого ключа. Это не пароль учётной записи сервера, а локальная защита ключевого файла.

В результате создаются два файла:

- `id_ed25519` — закрытый ключ;
- `id_ed25519.pub` — открытый ключ.

В некоторых старых системах Ed25519 недоступен. Выбор другого алгоритма следует согласовать с политикой безопасности и возможностями сервера.

## Шаг 3. Добавить открытый ключ на Linux-сервер

### Вариант А. Через ssh-copy-id

Если на локальном компьютере доступна команда `ssh-copy-id`, выполнить:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@example.com
```

Заменить `user` и `example.com` на действительные значения. Для первоначального добавления ключа обычно потребуется пароль учётной записи сервера.

### Вариант Б. Вручную

На локальном компьютере открыть файл `id_ed25519.pub` и скопировать **всю строку** открытого ключа, начинающуюся с `ssh-ed25519`.

На сервере под нужным пользователем выполнить:

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
nano ~/.ssh/authorized_keys
```

Добавить ключ отдельной строкой, сохранить файл и назначить права:

```bash
chmod 600 ~/.ssh/authorized_keys
```

Не следует копировать содержимое закрытого файла `id_ed25519`. Если пользовательский каталог или `.ssh` имеет неподходящие права либо владельца, сервер может игнорировать ключ.

## Шаг 4. Проверить подключение

В новом окне терминала выполнить:

```bash
ssh user@example.com
```

Если ключ сохранён с нестандартным именем:

```bash
ssh -i ~/.ssh/id_ed25519_server user@example.com
```

При первом подключении необходимо проверить отпечаток ключа сервера по доверенному каналу. Не рекомендуется без проверки подтверждать неизвестный сервер.

При запросе парольной фразы ключа введите именно её. Успешный вход без пароля учётной записи означает, что аутентификация по ключу работает.

Для диагностики используется подробный режим:

```bash
ssh -v user@example.com
```

## Шаг 5. Отключить вход по паролю — только после проверки

Если политикой безопасности предусмотрен исключительно вход по ключам, можно изменить конфигурацию SSH-сервера. **Сначала откройте второе независимое SSH-соединение по ключу и убедитесь, что оно работает. Текущую сессию не закрывайте.**

На сервере проверьте конфигурационные файлы `sshd`, включая возможные файлы в `sshd_config.d`. Затем задайте согласованную настройку:

```text
PasswordAuthentication no
```

Проверить синтаксис конфигурации (путь может отличаться по дистрибутивам):

```bash
sudo /usr/sbin/sshd -t
```

Только при отсутствии ошибок применить конфигурацию, например на Ubuntu:

```bash
sudo systemctl reload ssh
```

На некоторых системах служба называется `sshd`. Возможные другие методы входа, например keyboard-interactive, следует учитывать отдельно: одна директива `PasswordAuthentication no` не гарантирует запрет всех вариантов парольной аутентификации.

## Если SSH всё равно запрашивает пароль сервера

Проверьте расположение ключа, его соответствие записи в `authorized_keys`, права на каталог `.ssh`, владельца файлов и настройки `AuthorizedKeysFile`. Убедитесь, что подключение выполняется под тем пользователем, в домашнем каталоге которого установлен открытый ключ. Затем используйте `ssh -v` и журналы SSH-сервера для диагностики.

## Как защитить ключи при резервном копировании

Резервная копия закрытого ключа требует защиты не ниже, чем оригинал. Хранить такие файлы на общедоступной флешке или в незащищённом облаке не следует. Потерянный или скомпрометированный ключ необходимо удалить из `authorized_keys` на всех серверах, где он использовался, и заменить новой парой.

## Итог

Самый безопасный порядок действий — проверить ключи, создать новую пару, разместить только открытый ключ на сервере, убедиться в работе подключения и лишь затем ограничивать вход по паролю.

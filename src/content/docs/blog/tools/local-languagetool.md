## 1. Введение

При разработке технической документации, программных спецификаций, руководств пользователя, технических заданий и других документов особое значение имеют грамотность, терминологическая согласованность и единообразие изложения.

Для автоматизации лингвистической проверки применяется **LanguageTool** — программная система, позволяющая обнаруживать орфографические, грамматические, пунктуационные и некоторые стилистические ошибки.

Обычно LanguageTool используется через облачный сервис, браузерное расширение или интеграцию с текстовым редактором. Однако существует и другой способ эксплуатации: **развертывание собственного сервера LanguageTool непосредственно на персональном компьютере**.

Такой сервер может работать под управлением Windows или Linux, принимать запросы от локальных программ и выполнять проверку текста без передачи его содержимого на серверы LanguageTool.

Это особенно актуально при работе с документами, содержащими коммерческую тайну, внутренние технические сведения, неопубликованные разработки и другую информацию ограниченного распространения.

В статье рассматриваются:

- возможности локального сервера LanguageTool и его отличия от облачного сервиса;
- установка на Windows и Linux;
- настройка взаимодействия с браузером, LibreOffice и другими приложениями;
- проверка текста через программный интерфейс API;
- автоматизация контроля качества технической документации;
- ограничения локального решения и сравнение с LanguageTool Premium.

В качестве дополнительного источника используется репозиторий [alsibir/languagetool](https://github.com/alsibir/languagetool). Базовой технической документацией служит [официальный проект LanguageTool](https://github.com/languagetool-org/languagetool).

## 2. Что представляет собой локальный сервер LanguageTool

LanguageTool состоит из механизма лингвистического анализа, наборов правил проверки и программных интерфейсов, через которые внешние приложения обращаются к системе.

При локальном развертывании сервер запускается на компьютере пользователя и предоставляет HTTP API.

```text
Локальный компьютер
 ├── Браузер ─────────────┐
 ├── Текстовый редактор ──┼──> LanguageTool Server
 └── Скрипт / API ────────┘     127.0.0.1:8081
                                    │
                              Проверка текста
```

*Рисунок 1 — Схема взаимодействия приложений с локальным сервером LanguageTool.*

Принцип работы следующий:

1. Пользователь вводит или открывает текст в приложении.
2. Приложение передает текст серверу LanguageTool посредством HTTP-запроса.
3. Сервер выполняет лингвистический анализ.
4. Результат проверки возвращается в формате JSON.
5. Приложение отображает обнаруженные ошибки, пояснения и предлагаемые исправления.

По умолчанию для локального сервера часто используется адрес `http://localhost:8081`.

Основной метод проверки: `http://localhost:8081/v2/check`.

Список поддерживаемых языков: `http://localhost:8081/v2/languages`.

**Важно:** локальный сервер LanguageTool является прежде всего механизмом проверки текста и API. Полноценный графический редактор, аналогичный облачному интерфейсу LanguageTool, в стандартный сервер не входит. Для удобной работы требуется подключение совместимого приложения или разработка собственного интерфейса.

## 3. Что дает собственный сервер

### 3.1. Локальная обработка документов

Главное преимущество — возможность выполнять проверку текста внутри контролируемой вычислительной среды.

При правильной настройке серверу не требуется передавать проверяемый текст во внешнюю облачную службу.

Это позволяет использовать LanguageTool для работы с внутренней документацией организации при соблюдении установленной политики информационной безопасности.

Однако локальная установка сама по себе не гарантирует полного отсутствия сетевых обращений. Отдельные клиентские приложения могут использовать облачные функции, а установщик и дополнительные компоненты — загружать обновления и языковые данные.

Для обработки конфиденциальных документов рекомендуется отдельно проверять настройки клиентов и исходящие сетевые соединения.

### 3.2. Независимость от облачного сервиса

После установки необходимых компонентов локальный сервер может работать без подключения к Интернету. Это позволяет выполнять проверки при отсутствии доступа к внешним ресурсам, а также в изолированных сетях.

### 3.3. Автоматизация обработки документов

Наличие HTTP API позволяет использовать LanguageTool в собственных программных решениях.

Например, можно разработать скрипт PowerShell или Python, который извлекает текст из файлов DOCX, TXT или Markdown, отправляет его на проверку и формирует отчет об обнаруженных ошибках.

При этом важно учитывать, что стандартный API LanguageTool принимает текст, а не готовый файл DOCX. Извлечение текста, сохранение привязки замечаний к исходным абзацам и внесение исправлений должны выполняться внешней программой.

### 3.4. Настройка правил проверки

Открытая версия LanguageTool допускает создание и изменение правил проверки. Это позволяет использовать ее как основу для корпоративной системы контроля текстов.

Например, дополнительные правила могут обнаруживать нежелательные формулировки, некорректное употребление терминов и отдельные нарушения принятого стиля документации.

Однако **LanguageTool не является готовой системой проверки соответствия ГОСТ**. Для проверки структуры документа, оформления таблиц, ссылок, нумерации, реквизитов и других формальных требований необходимы дополнительные средства.

### 3.5. Контроль над инфраструктурой

Владелец локального сервера самостоятельно определяет:

- установленную версию LanguageTool;
- доступность сервера другим приложениям;
- состав дополнительных словарей и правил;
- параметры запуска и ограничения ресурсов;
- порядок обновления и резервного копирования.

При этом сопровождение сервера, контроль безопасности и устранение ошибок становятся ответственностью его администратора.

## 4. Будет ли локальный LanguageTool уступать Premium

Краткий ответ: **да, по ряду лингвистических и интеллектуальных функций локальная бесплатная версия уступает LanguageTool Premium. Однако для автоматизированной проверки технических документов собственный сервер может оказаться более подходящим решением.**

Причина заключается в различиях между открытым ядром LanguageTool и коммерческой облачной платформой.

Самостоятельно установленный сервер предоставляет базовую версию без облачных правил на основе искусственного интеллекта. Функции Premium не становятся доступными автоматически после установки сервера.

| Критерий | Локальный сервер | LanguageTool Premium |
|---|---|---|
| Орфографическая проверка | Да | Да |
| Грамматическая проверка | Да, открытые правила | Да, включая дополнительные правила |
| Пунктуация | Да, в пределах доступных правил | Более широкий набор проверок |
| Стилистические рекомендации | Базовые правила | Расширенные возможности |
| Перефразирование с помощью ИИ | Не входит в стандартный сервер | Доступно в рамках возможностей тарифа |
| Работа без Интернета | Да, после подготовки | Облачные функции требуют соединения |
| Локальное хранение проверяемого текста | Возможно | Обработка выполняется в облачной инфраструктуре |
| Собственный HTTP API | Да | Предоставление API зависит от продукта и условий обслуживания |
| Пользовательские правила | Возможны | Пользовательские словари и руководства по стилю зависят от тарифа |
| Самостоятельное администрирование | Требуется | Не требуется для облачного сервиса |
| Стоимость | Без платы за лицензию открытого ядра | Платная подписка |

Сведения о функциях Premium: [официальная страница тарифов](https://languagetool.org/ru/premium).

При оценке качества русскоязычной проверки следует учитывать, что количество и эффективность правил различаются в зависимости от языка. Наличие определенной функции в Premium не означает, что она одинаково реализована для русского, английского и других языков.

Поэтому объективное сравнение целесообразно проводить на собственном контрольном наборе документов.

Для технического писателя наиболее значимыми критериями будут не только количество найденных ошибок, но и число ложных замечаний, корректность обработки профессиональной терминологии и возможность автоматизации.

## 5. Подготовка к установке

### 5.1. Выбор способа развертывания

| Способ | Windows | Linux | Особенности |
|---|---|---|---|
| Запуск через Java | Да | Да | Минимум дополнительных компонентов |
| Docker | Да | Да | Изолированное окружение, удобное сопровождение |
| Сборка из исходного кода | Да | Да | Возможность модификации и разработки собственных правил |

Для первоначального развертывания рекомендуется **использовать готовый серверный пакет и Java**. Этот вариант не требует контейнеризации и позволяет понять принцип работы системы.

Docker целесообразен для постоянной эксплуатации, особенно если на компьютере уже используются контейнерные приложения.

Сборка из исходного кода требуется при необходимости модификации ядра LanguageTool, разработки дополнительных компонентов или получения собственной сборки из конкретной версии репозитория.

### 5.2. Требования к компьютеру

| Компонент | Рекомендация |
|---|---|
| Операционная система | Windows 10/11, современный Linux |
| Процессор | x86-64, 2 ядра и более |
| Оперативная память | От 4 ГБ; желательно 8 ГБ |
| Свободное место | От 2 ГБ без дополнительных моделей |
| Java | Совместимая с выбранной версией LanguageTool |
| Сеть | Интернет для первоначальной загрузки |
| TCP-порт | 8081 |

Это практические ориентиры, а не официальные минимальные требования. При использовании больших языковых моделей, нескольких одновременных клиентов и дополнительных словарей потребление памяти может существенно увеличиться.

Для сборки исходного кода требования к Java и Maven необходимо проверять по README выбранной версии репозитория.

## 6. Установка сервера LanguageTool в Windows

### Шаг 1. Установить Java

Рекомендуется использовать поддерживаемую сборку OpenJDK, например [Eclipse Temurin](https://adoptium.net/).

После установки открыть PowerShell и проверить доступность Java:

```powershell
java -version
```

В результате должна отображаться информация об установленной версии Java.

Если команда не найдена, необходимо проверить установку Java и переменную среды `PATH`.

### Шаг 2. Скачать LanguageTool

Открыть официальную инструкцию: [LanguageTool Embedded HTTP Server](https://dev.languagetool.org/http-server.html).

Перейти по ссылке на актуальный архив `LanguageTool-latest-snapshot.zip` и сохранить его на компьютере.

Следует учитывать, что snapshot представляет собой сборку для разработки и может содержать изменения, еще не включенные в стабильный выпуск. Для постоянной эксплуатации желательно зафиксировать проверенную версию.

### Шаг 3. Распаковать архив

Создать каталог `C:\LanguageTool`.

Распаковать в него содержимое архива так, чтобы в рабочем каталоге находился файл `languagetool-server.jar`.

Если архив содержит дополнительный вложенный каталог, дальнейшие команды необходимо выполнять из этого каталога.

### Шаг 4. Создать конфигурационный файл

В рабочем каталоге создать пустой файл `server.properties`.

Для базового запуска дополнительные параметры не требуются.

```powershell
Set-Location "C:\LanguageTool"
New-Item -ItemType File -Path ".\server.properties" -Force
```

### Шаг 5. Запустить сервер

```powershell
Set-Location "C:\LanguageTool"

java -cp languagetool-server.jar `
  org.languagetool.server.HTTPServer `
  --config server.properties `
  --port 8081 `
  --allow-origin
```

| Параметр | Назначение |
|---|---|
| `-cp` | Указывает Java архив с серверным приложением |
| `org.languagetool.server.HTTPServer` | Основной класс сервера |
| `--config` | Путь к файлу конфигурации |
| `--port 8081` | Порт приема HTTP-запросов |
| `--allow-origin` | Разрешает обращения из браузерных клиентов с других источников |

Для использования только из PowerShell или Python параметр `--allow-origin` не обязателен.

После запуска окно PowerShell должно оставаться открытым. Закрытие окна обычно приводит к завершению серверного процесса.

### Шаг 6. Проверить работу

Открыть в браузере: <http://localhost:8081/v2/languages>.

Если сервер запущен, будет возвращен список поддерживаемых языков в формате JSON.

Затем выполнить в другом окне PowerShell:

```powershell
$body = @{
    language = "ru"
    text = "В этом предложении есть ашибка."
}

$result = Invoke-RestMethod `
    -Uri "http://localhost:8081/v2/check" `
    -Method Post `
    -Body $body

$result.matches |
    Select-Object message, offset, length
```

В ответе должны появиться обнаруженные замечания, если установленный набор правил распознает ошибки в тестовой строке.

### Шаг 7. Создать сценарий запуска

Создать файл `start-languagetool.ps1`:

```powershell
$ErrorActionPreference = "Stop"

$serverPath = "C:\LanguageTool"

Set-Location $serverPath

java -Xms256m -Xmx2g `
    -cp languagetool-server.jar `
    org.languagetool.server.HTTPServer `
    --config server.properties `
    --port 8081 `
    --allow-origin
```

Параметры `-Xms256m` и `-Xmx2g` задают начальный и максимальный размер кучи Java. Значения допускается изменять в зависимости от объема доступной памяти.

Запуск:

```powershell
powershell.exe -NoProfile -File "C:\LanguageTool\start-languagetool.ps1"
```

При необходимости сервер можно оформить как службу Windows с помощью специализированного диспетчера служб. Для постоянной эксплуатации следует также настроить перезапуск после сбоя, журналирование и запуск от отдельной учетной записи с ограниченными правами.

## 7. Установка сервера LanguageTool в Linux

В качестве примера используется Ubuntu или Debian. Для других дистрибутивов потребуется заменить команды установки пакетов.

### Шаг 1. Установить Java

```bash
sudo apt update
sudo apt install -y openjdk-17-jre-headless curl unzip
java -version
```

Java 17 приведена как практический пример. Если выбранная сборка LanguageTool требует более новую версию, необходимо установить соответствующую Java.

### Шаг 2. Подготовить каталог

```bash
mkdir -p "$HOME/LanguageTool"
cd "$HOME/LanguageTool"
```

### Шаг 3. Загрузить архив

С официальной страницы сервера необходимо получить адрес актуального ZIP-архива.

Загрузка может выполняться браузером или командой `curl` с фактическим URL архива:

```bash
curl -fL \
  "URL_АКТУАЛЬНОГО_ZIP_АРХИВА" \
  -o LanguageTool.zip
```

Здесь `URL_АКТУАЛЬНОГО_ZIP_АРХИВА` — обозначение, которое требуется заменить действительным адресом загрузки.

После скачивания:

```bash
unzip LanguageTool.zip
```

Перейти в каталог, содержащий `languagetool-server.jar`.

### Шаг 4. Создать конфигурацию

```bash
touch server.properties
```

### Шаг 5. Запустить сервер

```bash
java -Xms256m -Xmx2g \
  -cp languagetool-server.jar \
  org.languagetool.server.HTTPServer \
  --config server.properties \
  --port 8081 \
  --allow-origin
```

### Шаг 6. Проверить API

В отдельном терминале:

```bash
curl -sS \
  --data-urlencode "language=ru" \
  --data-urlencode "text=В этом предложении есть ашибка." \
  http://127.0.0.1:8081/v2/check
```

Сервер должен вернуть JSON с результатом анализа.

### Шаг 7. Настроить автоматический запуск через systemd

Для постоянной эксплуатации рекомендуется создать отдельного системного пользователя, разместить сервер в `/opt/languagetool` и предоставить этому пользователю необходимые права чтения.

Пример файла `/etc/systemd/system/languagetool.service`:

```ini
[Unit]
Description=Local LanguageTool Server
After=network.target

[Service]
Type=simple
User=languagetool
Group=languagetool
WorkingDirectory=/opt/languagetool
ExecStart=/usr/bin/java -Xms256m -Xmx2g -cp languagetool-server.jar org.languagetool.server.HTTPServer --config server.properties --port 8081
Restart=on-failure
RestartSec=5
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

В данном примере предполагается, что пользователь и группа `languagetool` уже созданы, файлы находятся в `/opt/languagetool`, а Java доступна по пути `/usr/bin/java`.

После создания службы:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now languagetool
sudo systemctl status languagetool
```

Для просмотра журнала:

```bash
journalctl -u languagetool -f
```

Для остановки:

```bash
sudo systemctl stop languagetool
```

При такой конфигурации сервер автоматически запускается после загрузки Linux.

## 8. Альтернативная установка через Docker

Docker позволяет одинаковым способом развернуть сервер в Linux и Windows, если установлен Docker Engine или Docker Desktop.

Официальный проект LanguageTool перечисляет несколько контейнерных сборок, поддерживаемых сообществом. Они не являются официальными образами основной команды разработки.

В качестве примера используется [meyayl/docker-languagetool](https://github.com/meyayl/docker-languagetool).

### Шаг 1. Проверить Docker

```bash
docker --version
docker compose version
```

### Шаг 2. Создать конфигурационный файл

Создать каталог `languagetool-docker`, а внутри — файл `compose.yaml`.

```yaml
services:
  languagetool:
    image: meyay/languagetool:latest
    container_name: languagetool
    restart: unless-stopped

    ports:
      - "127.0.0.1:8081:8081"

    environment:
      JAVA_XMS: "256m"
      JAVA_XMX: "2g"

    security_opt:
      - no-new-privileges:true
```

Привязка порта к `127.0.0.1` ограничивает доступ локальным компьютером.

Использование тега `latest` удобно для первого запуска. Для воспроизводимой установки рекомендуется впоследствии зафиксировать конкретную версию образа или его digest.

### Шаг 3. Запустить контейнер

В каталоге с `compose.yaml`:

```bash
docker compose up -d
```

Проверить состояние:

```bash
docker compose ps
docker compose logs --tail=50
```

### Шаг 4. Проверить сервер

Открыть `http://127.0.0.1:8081/v2/languages`.

### Шаг 5. Управлять контейнером

| Операция | Команда |
|---|---|
| Запуск | `docker compose up -d` |
| Остановка | `docker compose stop` |
| Повторный запуск | `docker compose restart` |
| Просмотр журнала | `docker compose logs -f` |
| Удаление контейнера | `docker compose down` |

Для установки на Windows и Linux используется один и тот же файл Compose.

При работе в Windows с Docker Desktop необходимо учитывать, что контейнер запускается в виртуализированной среде Linux. Это не мешает приложениям Windows обращаться к опубликованному порту `localhost`.

## 9. Как работать с локальным LanguageTool

После установки сервер необходимо подключить к программам, в которых выполняется редактирование документов.

### 9.1. Подключение браузерного расширения

Браузерное расширение LanguageTool позволяет проверять текст в веб-формах и редакторах.

В настройках совместимых версий расширения предусмотрена возможность выбора локального сервера.

Последовательность подключения:

1. Установить официальное расширение LanguageTool для Firefox, Chrome или другого поддерживаемого браузера.
2. Открыть настройки расширения.
3. Перейти в раздел экспериментальных или расширенных настроек.
4. Найти параметр выбора сервера.
5. Выбрать локальный сервер либо указать пользовательский адрес, если такая возможность предусмотрена версией расширения.
6. Сохранить настройки.
7. Проверить текст в тестовом поле ввода.

Для пользовательского адреса обычно используется базовый путь `http://localhost:8081/v2`.

В официальной инструкции описана настройка Local server в экспериментальных параметрах расширения. Расположение и наличие этого переключателя могут изменяться между версиями.

Следует учитывать, что некоторые браузерные расширения и веб-сайты требуют HTTPS, а отдельные функции расширения могут продолжать обращаться к облачным сервисам.

**При работе с конфиденциальными документами необходимо проверить фактические сетевые обращения расширения, а не полагаться исключительно на выбранный адрес локального сервера.**

### 9.2. Использование с LibreOffice

Для LibreOffice существуют средства интеграции LanguageTool, позволяющие проверять документы непосредственно в текстовом редакторе.

Конкретные параметры подключения зависят от установленной версии расширения.

Общий порядок настройки:

1. Установить совместимое расширение LanguageTool.
2. Перезапустить LibreOffice.
3. Открыть параметры расширения.
4. Проверить наличие настройки локального сервера.
5. При наличии такой настройки указать адрес `http://127.0.0.1:8081/v2`.
6. Выполнить проверку тестового документа.

Не все версии расширения поддерживают подключение к внешнему локальному HTTP-серверу одинаковым образом. Некоторые сборки используют собственный встроенный механизм LanguageTool. Поэтому перед внедрением необходимо проверить совместимость конкретной версии LibreOffice и расширения.

### 9.3. Использование с Microsoft Word

Для Microsoft Word ситуация отличается.

Официальная интеграция LanguageTool для Word не должна автоматически рассматриваться как клиент произвольного локального сервера.

Наличие установленного LanguageTool на компьютере не означает, что надстройка Word начнет обращаться к нему вместо облачного сервиса.

Для локальной проверки документов DOCX можно использовать отдельную программу, которая:

1. Открывает документ.
2. Извлекает текст абзацев, таблиц, заголовков и других элементов.
3. Передает текст на локальный сервер.
4. Получает результаты проверки.
5. Формирует отчет с указанием мест обнаружения ошибок.
6. При необходимости создает копию документа с комментариями.

Такой подход позволяет интегрировать LanguageTool с собственными средствами автоматизации Word, включая PowerShell и Python.

## 10. Проверка текста через API

Наиболее универсальный способ работы с собственным сервером — использование HTTP API.

### 10.1. Формирование запроса

Для проверки используется метод `POST /v2/check`.

| Параметр | Назначение | Пример |
|---|---|---|
| `text` | Проверяемый текст | `Это тестовый текст` |
| `language` | Язык проверки | `ru` |
| `enabledRules` | Включаемые правила | Идентификаторы правил |
| `disabledRules` | Отключаемые правила | Идентификаторы правил |
| `enabledCategories` | Включаемые категории | Идентификаторы категорий |
| `disabledCategories` | Отключаемые категории | Идентификаторы категорий |

Поддержка дополнительных параметров зависит от версии сервера. Полное описание доступно в [документации HTTP API](https://languagetool.org/http-api/swagger-ui/).

### 10.2. Пример на Python

```python
import requests

SERVER_URL = "http://127.0.0.1:8081/v2/check"

text = (
    "Данная программа предназначен "
    "для проверки технических документов."
)

response = requests.post(
    SERVER_URL,
    data={
        "language": "ru",
        "text": text,
    },
    timeout=60,
)

response.raise_for_status()
result = response.json()

for match in result.get("matches", []):
    print("Замечание:", match["message"])
    print("Позиция:", match["offset"])
    print("Длина:", match["length"])

    replacements = match.get("replacements", [])
    if replacements:
        print("Предложение:", replacements[0]["value"])

    print()
```

Перед выполнением необходимо установить библиотеку:

```bash
python -m pip install requests
```

Пример использует открытый API и не требует учетной записи LanguageTool Premium.

### 10.3. Пример на PowerShell

```powershell
$uri = "http://127.0.0.1:8081/v2/check"

$text = @"
Данная программа предназначен для проверки документов.
Система обеспечивают обработку текста.
"@

$response = Invoke-RestMethod `
    -Uri $uri `
    -Method Post `
    -Body @{
        language = "ru"
        text = $text
    }

foreach ($match in $response.matches) {
    Write-Host "Замечание: $($match.message)"
    Write-Host "Позиция: $($match.offset)"

    if ($match.replacements.Count -gt 0) {
        Write-Host "Исправление: $($match.replacements[0].value)"
    }

    Write-Host ""
}
```

Результаты проверки можно сохранить в CSV, JSON или использовать для создания отдельного отчета.

Следует учитывать, что поля `offset` и `length` описывают позиции в переданном тексте, а не координаты элементов документа Word. Для точной привязки замечаний к DOCX требуется дополнительная логика сопоставления.

## 11. Применение при разработке технической документации

Для технического писателя локальный LanguageTool представляет интерес не только как средство исправления орфографии.

Его можно включить в многоэтапную систему автоматизированного контроля качества документации.

```text
Документы DOCX, MD, TXT
          |
          v
Извлечение текста и структуры
          |
          v
Локальный LanguageTool
          |
          v
Дополнительные правила и проверка ГОСТ
          |
          v
Отчет о замечаниях
```

*Рисунок 2 — Возможная схема автоматизированного контроля качества технической документации.*

### 11.1. Проверка терминологической согласованности

В технических документах часто используются специализированные термины, сокращения и наименования компонентов.

Например:

- программное обеспечение;
- программно-аппаратный комплекс;
- автоматизированная система;
- программный интерфейс;
- эксплуатационная документация.

Для обеспечения единообразия можно создать отдельные правила проверки, запрещающие определенные варианты терминов или рекомендующие утвержденные формулировки.

При этом необходимо отличать орфографический словарь от корпоративного терминологического справочника. Добавление слова в словарь не обеспечивает автоматическую проверку всех правил его употребления.

### 11.2. Проверка формулировок требований

При разработке технических заданий могут встречаться неоднозначные формулировки:

> Система должна обеспечивать достаточно быстрое выполнение операций.

Подобное требование не содержит измеримого критерия.

С помощью пользовательских правил можно обнаруживать отдельные нежелательные конструкции, например «достаточно быстро», «при необходимости», «по возможности».

Однако выявление таких слов не равнозначно полноценному семантическому анализу требований. Для оценки проверяемости, непротиворечивости и полноты требований необходимы дополнительные алгоритмы или экспертная проверка.

### 11.3. Контроль соблюдения ГОСТ

Для документов, оформляемых по ГОСТ, LanguageTool может использоваться в составе комплексного средства проверки.

| Проверяемый объект | Средство |
|---|---|
| Орфография | LanguageTool |
| Грамматика | LanguageTool |
| Пунктуация | LanguageTool |
| Терминология | Пользовательские правила и словари |
| Структура документа | Отдельный анализатор DOCX |
| Нумерация разделов | Анализатор структуры |
| Оформление таблиц | Анализатор DOCX |
| Перекрестные ссылки | Анализатор связей |
| Требования ГОСТ | Специализированный набор проверок |

Таким образом, LanguageTool может выполнять лингвистическую часть контроля, а специализированные скрипты — структурную и нормативную.

## 12. Можно ли расширить локальный LanguageTool до уровня Premium

Теоретически локальную систему можно существенно усовершенствовать. Однако необходимо различать расширение возможностей открытой версии и получение функций коммерческого продукта.

### 12.1. Дополнительные правила

LanguageTool поддерживает разработку пользовательских правил.

Для простых закономерностей могут применяться шаблонные правила, а для более сложных проверок — программная реализация.

Это позволяет адаптировать систему к требованиям конкретной организации.

### 12.2. Дополнительные языковые данные

Некоторые проверки могут использовать статистические языковые данные, в частности n-граммные модели.

Для определенных языков такие данные позволяют улучшить качество обнаружения отдельных ошибок.

Но наличие дополнительных моделей не превращает открытую версию в Premium и не обеспечивает автоматически доступ к облачным алгоритмам.

### 12.3. Подключение локальной языковой модели

Наиболее интересный вариант — совместное использование LanguageTool и локальной большой языковой модели.

Например, можно построить систему, в которой:

1. LanguageTool обнаруживает орфографические и грамматические ошибки.
2. Локальная языковая модель анализирует стилистику и смысловую ясность.
3. Дополнительный анализатор проверяет терминологию.
4. Отдельный модуль контролирует требования ГОСТ.
5. Программа формирует объединенный отчет.

Для запуска языковой модели могут применяться Ollama, llama.cpp и другие локальные средства инференса.

Однако такая интеграция требует отдельной разработки. Она не входит в стандартный сервер LanguageTool.

Кроме того, языковые модели могут изменять смысл текста, предлагать некорректные технические формулировки и создавать ложные замечания. Поэтому автоматическое принятие исправлений в технической документации не рекомендуется.

## 13. Обеспечение безопасности локального сервера

При работе с документами ограниченного распространения необходимо учитывать следующие требования.

### 13.1. Ограничить сетевой доступ

Для персонального использования сервер должен принимать соединения только с локального компьютера.

В Docker это достигается публикацией порта через `127.0.0.1`.

При обычном запуске Java официальный сервер по умолчанию не предоставляет доступ удаленным узлам без специального параметра `--public`.

Не рекомендуется использовать `--public` без необходимости.

### 13.2. Не публиковать API в Интернет

Стандартный локальный сервер не следует считать готовой защищенной многопользовательской системой.

Если доступ необходим из локальной сети, рекомендуется использовать обратный прокси с TLS, аутентификацией и ограничением доступа по сетевым адресам.

### 13.3. Проверять клиентские приложения

Даже если сервер работает локально, браузерное расширение или другое приложение может иметь дополнительные облачные функции.

Для конфиденциальной документации следует:

- отключить ненужные облачные возможности;
- проверить фактические сетевые соединения;
- исключить отправку текста в сторонние сервисы;
- использовать доверенные версии программ;
- контролировать журналы, временные файлы и резервные копии.

### 13.4. Фиксировать версии компонентов

Для воспроизводимости результатов рекомендуется фиксировать версии сервера, Java, словарей и пользовательских правил.

Это особенно важно, если проверка выполняется в рамках регламентированного процесса контроля качества документации.

## 14. Типичные проблемы и способы устранения

| Проблема | Возможная причина | Решение |
|---|---|---|
| Java не запускается | Java отсутствует или не включена в `PATH` | Проверить `java -version` |
| Не найден `languagetool-server.jar` | Неверный рабочий каталог | Проверить расположение файла |
| Порт 8081 занят | Работает другой процесс | Освободить порт или выбрать другой |
| API недоступен | Сервер не запущен | Проверить процесс и журнал |
| Браузер не подключается | Неверный URL или ограничения расширения | Проверить адрес и настройки |
| Проверка выполняется медленно | Недостаточно памяти или большой текст | Увеличить доступную память, разбить текст |
| Некоторые ошибки не обнаруживаются | Ограничения правил | Проверить язык и доступные правила |
| Отличаются результаты от Premium | Разный состав механизмов проверки | Сравнить версии и функциональность |
| Служба Linux не запускается | Ошибка пути или прав | Проверить `journalctl` |
| Docker-контейнер завершается | Ошибка конфигурации или недостаток ресурсов | Проверить `docker compose logs` |

## 16. Заключение

Развертывание собственного сервера LanguageTool на Windows или Linux позволяет получить независимый инструмент автоматизированной лингвистической проверки текстов.

Основные преимущества такого решения — локальная обработка документов, доступность программного интерфейса, возможность создания дополнительных правил и интеграция с собственными средствами автоматизации.

При этом локальная бесплатная версия не является полноценным аналогом LanguageTool Premium. Коммерческий сервис предоставляет дополнительные проверки и интеллектуальные функции, недоступные в стандартной открытой сборке.

Для профессионального технического писателя оптимальным может оказаться не выбор между локальным сервером и Premium, а создание собственной системы контроля качества документации, в которой LanguageTool выполняет проверку языка, дополнительные программы контролируют структуру и нормативные требования, а локальная языковая модель используется для анализа сложных формулировок.

**Главный результат внедрения — возможность организовать воспроизводимую, автоматизированную и контролируемую проверку технических документов без обязательной передачи их содержимого во внешние облачные сервисы.**

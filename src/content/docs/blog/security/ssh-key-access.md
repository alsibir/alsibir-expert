SSH позволяет администрировать удалённый сервер через защищённое соединение. При обычном входе пользователь вводит пароль учётной записи. Альтернативный вариант — **аутентификация по паре криптографических ключей**: открытый ключ размещается на сервере, а закрытый остаётся у пользователя.

В этой инструкции рассмотрена настройка доступа с компьютера под управлением Windows через **PuTTY** к серверу Linux с **OpenSSH**. Отдельное внимание уделено журналированию: по отпечатку открытого ключа можно определить, **какой именно ключ использовался при подключении**.

В результате настройки пользователь сможет:

- создать пару SSH-ключей с помощью PuTTYgen;
- установить открытый ключ в учётную запись сервера;
- подключиться через PuTTY с закрытым ключом в формате `.ppk`;
- включить дополнительную детализацию журналов OpenSSH;
- сопоставить запись об успешном входе с определённым ключом;
- проверить типичные причины отказа в подключении.

> **Важно.** В исходном материале ключи названы «сертификатами». В описанном сценарии используются **обычные SSH-ключи**, а не сертификаты OpenSSH, подписанные центром сертификации. Это разные механизмы. Далее применяется технически корректное название — «аутентификация по открытому ключу».

## 1. Как работает SSH-доступ по ключам

Пара ключей состоит из двух связанных компонентов:

| Компонент | Назначение | Где хранится |
| --- | --- | --- |
| Открытый ключ | Позволяет серверу проверить подтверждение владения закрытым ключом | На сервере, обычно в `~/.ssh/authorized_keys` |
| Закрытый ключ | Используется клиентом для доказательства владения парой ключей | На компьютере пользователя; для PuTTY — обычно файл `.ppk` |
| Парольная фраза (passphrase) | Дополнительно защищает закрытый ключ в случае копирования его файла | Не передаётся серверу как пароль учётной записи |

Закрытый ключ **не требуется копировать на сервер**. При подключении клиент доказывает владение им с помощью криптографической операции, а сервер проверяет результат по сохранённому открытому ключу.

Аутентификация по ключу не исключает другие способы входа автоматически. До изменения конфигурации сервер может принимать как ключи, так и пароли. Отключать парольный вход следует только после проверки, что вход по ключу действительно работает.

### Что потребуется

- Компьютер с Windows и установленными PuTTY и PuTTYgen.
- Сервер Linux с работающей службой OpenSSH (`sshd`).
- Адрес сервера и имя учётной записи для подключения.
- Первоначальный доступ к этой учётной записи для изменения файла `authorized_keys`.
- Права администратора сервера — только для изменения конфигурации `sshd` и проверки системных журналов, если обычному пользователю они недоступны.

**Рекомендуемый вариант:** подключение под отдельной учётной записью, например `admin`, с получением административных прав через `sudo`. Прямой вход по SSH под `root` допустим только там, где он обоснован требованиями эксплуатации и разрешён политикой безопасности.

## 2. Создание пары ключей с помощью PuTTYgen

PuTTYgen — утилита из комплекта PuTTY, предназначенная для создания и управления SSH-ключами.

Загрузка: [официальная страница PuTTY](https://www.chiark.greenend.org.uk/~sgtatham/putty/latest.html).

1. Запустить `puttygen.exe` на компьютере с Windows.
2. В параметрах типа ключа выбрать **EdDSA / Ed25519**, если такой алгоритм поддерживается сервером. Для систем с ограниченной совместимостью выбирать тип ключа согласно их требованиям; при использовании RSA предпочтительна длина не менее 3072 бит.
3. Нажать **Generate**. Если приложение запросит случайные движения мышью, выполнить их до завершения формирования ключа.
4. В поле **Key comment** указать понятный идентификатор, например `admin-workstation-2026`. Комментарий упрощает сопровождение, но не является надёжным подтверждением личности владельца.
5. Заполнить **Key passphrase** и **Confirm passphrase** — задать парольную фразу для защиты закрытого ключа.
6. Нажать **Save private key** и сохранить файл, например `admin-workstation-2026.ppk`, в каталог с ограниченным доступом.
7. Найти поле **Public key for pasting into OpenSSH authorized_keys file** и полностью скопировать его содержимое. Именно эту строку необходимо добавить на сервер.

Образец формата открытого ключа (сокращён; **не является действительным ключом**):

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... admin-workstation-2026
```

В действительном ключе вся строка — тип, длинное значение и необязательный комментарий — должна сохраняться без разрывов.

### Чем отличаются кнопки сохранения ключей

**Save private key** сохраняет закрытый ключ в формате PuTTY (`.ppk`). Он выбирается в параметрах подключения PuTTY.

**Save public key** сохраняет открытый ключ в формате, который не всегда соответствует однострочному представлению, необходимому OpenSSH для `authorized_keys`. Поэтому для данного сценария надёжнее копировать содержимое поля **Public key for pasting into OpenSSH authorized_keys file**.

Парольную фразу рекомендуется использовать даже при хранении ключа на личном компьютере. Нельзя размещать закрытые ключи в публичных Git-репозиториях, отправлять их вместе с документацией или предоставлять другим администраторам.

## 3. Добавление открытого ключа на сервер Linux

Подключиться к серверу ранее доступным способом под **той учётной записью, для которой настраивается вход по ключу**. Например, если подключение планируется под `admin`, команды необходимо выполнять в его домашнем каталоге.

Создать каталог SSH и файл разрешённых ключей:

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
touch ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Команды выполняются **без `sudo`**, если пользователь уже вошёл под целевой учётной записью и имеет доступ к собственному домашнему каталогу.

Открыть файл для редактирования:

```bash
nano ~/.ssh/authorized_keys
```

Вставить в него **полную строку открытого ключа** из PuTTYgen, сохранить изменения и закрыть редактор. Если файл уже содержит другие ключи, новую строку следует добавить в конец, не удаляя действующие записи. Каждый ключ должен находиться на отдельной строке.

Повторно проверить права:

```bash
ls -ld ~ ~/.ssh
ls -l ~/.ssh/authorized_keys
```

Для типовой конфигурации рекомендуются права `700` на `.ssh` и `600` на `authorized_keys`. Домашний каталог не должен быть доступен для изменения посторонними пользователями. Владельцем каталога `.ssh` и файла `authorized_keys` должна быть соответствующая учётная запись.

**Для входа под `root`:** открытый ключ должен находиться в `/root/.ssh/authorized_keys`, а сервер должен разрешать соответствующий способ входа. Изменение файла другого пользователя не предоставит доступ к учётной записи `root`.

Перезапуск службы OpenSSH **не требуется**, когда изменяется только файл `authorized_keys`: новые записи используются при последующих попытках аутентификации.

## 4. Настройка подключения в PuTTY

1. Открыть PuTTY и перейти в раздел **Session**.
2. В поле **Host Name (or IP address)** указать адрес сервера.
3. Проверить тип соединения **SSH** и порт (обычно `22`, если администратор не установил другой).
4. При необходимости открыть **Connection → Data** и указать имя пользователя в поле **Auto-login username**.
5. Перейти в **Connection → SSH → Auth → Credentials**.
6. В поле **Private key file for authentication** нажать **Browse** и выбрать сохранённый файл `.ppk`.
7. Вернуться в **Session**, указать имя профиля в **Saved Sessions** и нажать **Save**.
8. Нажать **Open** и выполнить подключение.

При первом соединении следует проверить отображённый PuTTY отпечаток **ключа сервера** по доверенному источнику. Он отличается от отпечатка **пользовательского ключа**, который применяется для входа.

Если у закрытого ключа установлена парольная фраза, PuTTY запросит её. При успешном подключении должен открыться сеанс выбранной учётной записи.

> **Важно.** В старых версиях PuTTY параметр закрытого ключа располагался непосредственно в **Connection → SSH → Auth**. В современных версиях он находится в подразделе **Credentials**.

Проверку рекомендуется выполнять **в новом окне PuTTY**, сохраняя прежнее рабочее подключение. Это особенно важно перед изменением параметров аутентификации сервера.

## 5. Как определить, каким ключом выполнен вход

В журналах OpenSSH фиксируются успешные и неуспешные попытки аутентификации. В зависимости от версии сервера и уровня детализации записи об успешном входе могут содержать тип ключа и его отпечаток (fingerprint).

Отпечаток — это короткое представление криптографического хеша открытого ключа. Он используется для сопоставления записи в журнале с ключом, который зарегистрирован в `authorized_keys`.

### 5.1. Просмотр журналов

Для серверов Debian и Ubuntu, где используется запись в традиционные текстовые журналы:

```bash
sudo tail -n 50 /var/log/auth.log
```

Для серверов семейства RHEL, CentOS и совместимых систем, где существует соответствующий файл:

```bash
sudo tail -n 50 /var/log/secure
```

Для систем с `systemd-journald` удобно использовать:

```bash
sudo journalctl -u ssh -u sshd --since today --no-pager
```

Наличие конкретного файла или имени службы зависит от дистрибутива и его настроек. Отсутствие `/var/log/auth.log` само по себе не означает, что журналирование SSH отключено.

### 5.2. Пример записи об успешном входе

На современных версиях OpenSSH запись может иметь следующий вид (пример условный):

```text
Oct 26 14:05:01 server sshd[2345]: Accepted publickey for admin from 192.0.2.10 port 60234 ssh2: ED25519 SHA256:<отпечаток_ключа>
```

Здесь:

- `Accepted publickey` — вход с применением открытого ключа выполнен успешно;
- `admin` — имя учётной записи на сервере;
- `192.0.2.10` — IP-адрес клиента (демонстрационный адрес);
- `ED25519` — тип ключа;
- `SHA256:<отпечаток_ключа>` — отпечаток применённого ключа.

В старых версиях OpenSSH информация могла представляться иначе. Например, в исходной инструкции приведена запись CentOS 7 с отпечатком RSA в историческом формате MD5:

```text
Dec 4 21:32:40 server sshd[21379]: Accepted publickey for root from 10.1.3.221 port 56929 ssh2: RSA fa:7c:c6:6b:31:98:43:9f:ef:41:c5:49:80:c2:a8:16
```

Такие записи не следует считать образцом современного формата журнала. В актуальных конфигурациях предпочтительно сравнивать отпечатки **SHA256**, а не MD5.

### 5.3. Сопоставление отпечатка с установленным ключом

Вывести отпечатки ключей из файла разрешённых ключей:

```bash
ssh-keygen -lf ~/.ssh/authorized_keys -E sha256
```

Если в файле находится несколько ключей, команда может вывести несколько строк. Их следует сопоставить с данными журнала.

Отпечаток также можно посмотреть в PuTTYgen после загрузки соответствующего закрытого ключа. При сравнении необходимо использовать один и тот же формат отпечатков, предпочтительно SHA256.

**Ограничение:** отпечаток определяет **конкретный ключ**, а не автоматически личность пользователя. Для привязки действий к ответственному лицу каждому администратору необходимо выдавать индивидуальный ключ и вести актуальный перечень владельцев ключей. Использование общей пары ключей делает такой учёт недостоверным.

## 6. Включение подробного журналирования SSH

Если сообщения о подключениях не содержат сведений об используемом ключе, можно повысить детализацию журнала OpenSSH.

Открыть конфигурацию SSH-сервера:

```bash
sudo nano /etc/ssh/sshd_config
```

Установить параметр:

```text
LogLevel VERBOSE
```

Если директива уже существует, необходимо изменить её действующее значение, а не добавлять противоречащие строки. Также следует учитывать файлы, подключённые директивой `Include`, и блоки `Match`.

Перед применением проверить синтаксис:

```bash
sudo /usr/sbin/sshd -t
```

При отсутствии ошибок проверить фактическое значение параметра:

```bash
sudo /usr/sbin/sshd -T | grep '^loglevel '
```

Ожидаемое значение:

```text
loglevel VERBOSE
```

Для применения изменений выполнить **перезагрузку конфигурации**, не разрывая работающий сеанс:

**Debian / Ubuntu:**

```bash
sudo systemctl reload ssh
```

**RHEL / Fedora / CentOS (при имени службы `sshd`):**

```bash
sudo systemctl reload sshd
```

Если служба называется иначе или не поддерживает `reload`, способ применения определяется настройками конкретного сервера. До выполнения операции необходимо обеспечить резервный способ административного доступа.

Открыть **новое** SSH-соединение через PuTTY и просмотреть журнал повторно.

Уровень `VERBOSE` обычно добавляет сведения о ходе аутентификации и помогает идентифицировать использованный ключ. Отладочные уровни `DEBUG`, `DEBUG2` и `DEBUG3` не рекомендуется постоянно применять на рабочем сервере: они значительно увеличивают объём журналов и могут раскрывать дополнительные технические сведения о сеансах.

## 7. Дополнительное усиление безопасности

После подтверждения успешной аутентификации по ключу рекомендуется оценить следующие меры:

1. **Индивидуальные учётные записи.** Для совместного администрирования использовать отдельные учётные записи и, при необходимости, `sudo`, а не общий вход под `root`.
2. **Индивидуальные пары ключей.** Для каждого администратора и управляемого устройства использовать отдельные ключи, если это соответствует принятой модели управления доступом.
3. **Защита закрытого ключа.** Сохранять `.ppk` с парольной фразой и ограничивать доступ к файлу.
4. **Отзыв доступа.** При компрометации ключа удалить соответствующую строку из `authorized_keys` на всех серверах, где она применяется, и заменить ключ.
5. **Ограничение парольного входа.** Отключать его только после проверки входа по ключу и наличия резервного канала восстановления доступа.

Для сервера, на котором принят доступ **только по ключам** и запрещён прямой вход под `root`, могут использоваться следующие настройки в `sshd_config`:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
```

Это **пример политики**, а не обязательный набор команд для любой установки. Он изменяет доступность существующих способов аутентификации и может заблокировать подключение, если ключи или резервный доступ не подготовлены. После изменения конфигурации необходимо проверить `sshd -t`, фактические значения параметров и новое подключение.

Если по эксплуатационным причинам требуется прямой вход `root` с ключом, OpenSSH поддерживает значение `PermitRootLogin prohibit-password`, запрещающее парольный и интерактивный вход для `root`. Применение такой схемы требует отдельного обоснования и проверки политики доступа.

## 8. Распространённые проблемы

| Признак | Возможная причина | Рекомендуемая проверка |
| --- | --- | --- |
| PuTTY сообщает `Server refused our key` | Открытый ключ отсутствует в `authorized_keys`, повреждён или записан не одной строкой | Проверить содержимое файла целевой учётной записи |
| Сервер продолжает запрашивать пароль учётной записи | Клиент не предложил ключ или сервер отклонил его | Проверить путь к `.ppk`, имя пользователя и журнал `sshd` |
| Сообщение `Permission denied (publickey)` | Нет подходящего разрешённого ключа или подключение выполняется не под той учётной записью | Сопоставить пользователя, отпечатки ключей и параметры `PubkeyAuthentication` |
| Ключ присутствует, но не принимается | Неверные права или владелец каталога `.ssh` / файла `authorized_keys` | Проверить `ls -ld ~ ~/.ssh` и `ls -l ~/.ssh/authorized_keys` |
| Подключение под `root` не выполняется | Политика `PermitRootLogin` запрещает такой вход | Проверить действующие настройки `sshd` и использовать административную учётную запись |
| В журнале нет отпечатка ключа | Формат сообщений или уровень журналирования не содержит этих сведений | Проверить `LogLevel`, `sshd -T` и источник журналов |
| После изменения конфигурации вход перестал работать | Ошибка в настройках или отключён единственный доступный способ входа | Использовать сохранённое соединение или консоль сервера; восстановить конфигурацию |

На системах с SELinux дополнительной причиной отказа может быть некорректный контекст безопасности файла `authorized_keys`. Диагностика и восстановление контекстов выполняются с учётом политики конкретного дистрибутива.

## 9. Проверка результата

Настройка считается успешной, если выполнены все условия:

- [ ] В PuTTY выбран закрытый ключ `.ppk`, соответствующий открытому ключу на сервере.
- [ ] Открытый ключ добавлен в `~/.ssh/authorized_keys` нужной учётной записи.
- [ ] Права на `.ssh` и `authorized_keys` проверены.
- [ ] Новое подключение через PuTTY открывается с аутентификацией по ключу.
- [ ] В журналах сервера обнаружена запись об успешном входе.
- [ ] Отпечаток ключа в журнале сопоставлен с зарегистрированным ключом.
- [ ] Необходимость парольного входа и прямого доступа `root` отдельно оценена.
- [ ] Администратор сохранил возможность восстановления доступа к серверу.

## Заключение

Для настройки SSH-аутентификации по ключам достаточно создать пару ключей в PuTTYgen, поместить открытый ключ в `authorized_keys` нужного пользователя и указать закрытый `.ppk` в PuTTY. **Изменение `authorized_keys` само по себе не требует перезапуска SSH-сервера.**

Для аудита подключений важна не только запись о факте успешного входа, но и **отпечаток использованного ключа**. При необходимости детализация повышается параметром `LogLevel VERBOSE`. При этом надёжная идентификация администратора обеспечивается организацией доступа: индивидуальными учётными записями, отдельными ключами и контролируемым порядком их выдачи и отзыва.

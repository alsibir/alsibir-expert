Хорошая документация API отвечает не только на вопрос «какой запрос отправить», но и на вопросы «кто имеет право», «что произойдет при отказе», «какие данные изменятся» и «какие изменения нарушат совместимость». Контракт интерфейса служит точкой согласования серверной и клиентской команд.

## 1. Контракт как техническое соглашение

OpenAPI описывает HTTP API в машиночитаемом формате YAML или JSON. В спецификации **OpenAPI 3.1.1** определены структура документа, операции, параметры, схемы, ответы и механизмы безопасности. Описание должно быть согласовано с поведением реализации: валидный YAML, не соответствующий реальному сервису, не является достоверным контрактом.

Для каждой операции необходимо определить назначение, идентификатор, метод и путь, права доступа, входные данные, ответы, предельные случаи, побочные эффекты и правила повторных вызовов.

## 2. Демонстрационный контракт

**Вымышленный сервис:** просмотр заявки `GET /api/v1/requests/{request_id}`. Следующий фрагмент представляет самостоятельный минимальный документ OpenAPI 3.1.1:

```yaml
openapi: 3.1.1
info:
  title: Demo Requests API
  version: 1.0.0
servers:
  - url: https://api.example.invalid
paths:
  /api/v1/requests/{request_id}:
    get:
      operationId: get_request
      summary: Получить заявку по идентификатору
      security:
        - bearer_auth: []
      parameters:
        - name: request_id
          in: path
          required: true
          schema:
            type: string
            pattern: '^[A-Z]-[0-9]{4}$'
      responses:
        '200':
          description: Заявка найдена
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Request'
        '401':
          description: Требуется аутентификация
        '403':
          description: Недостаточно прав на объект
        '404':
          description: Заявка не найдена либо скрыта политикой доступа
components:
  securitySchemes:
    bearer_auth:
      type: http
      scheme: bearer
  schemas:
    Request:
      type: object
      required: [id, status]
      properties:
        id:
          type: string
          examples: ["R-1001"]
        status:
          type: string
          enum: [draft, approved, rejected]
```

Домен `.invalid` намеренно используется для демонстрационных примеров; его нельзя принимать за действующий адрес сервиса. Схема показывает структуру интерфейса, но не заменяет реализацию авторизации.

## 3. Модель ошибок, пригодная для интеграции

Для подробных ошибок HTTP API может применяться **RFC 9457 Problem Details**, в котором предусмотрен формат `application/problem+json`. Пример отказа:

```json
{
  "type": "https://example.invalid/problems/forbidden",
  "title": "Access denied",
  "status": 403,
  "detail": "Access to this request is not permitted",
  "instance": "/api/v1/requests/R-1001"
}
```

Не следует включать в ответ об ошибке внутренние SQL-запросы, трассировки с секретами, токены или сведения о существовании чужих объектов, если политика доступа это запрещает. При некоторых моделях безопасности ответ `404` может использоваться для сокрытия существования ресурса; решение документируется отдельно и проверяется тестами.

## 4. Авторизация: наличие токена еще не означает право доступа

Аутентификация устанавливает субъект запроса. Авторизация проверяет, имеет ли он право совершить действие над **конкретным объектом**. OWASP относит ошибки объектной авторизации к важнейшим рискам API. Для операции с `request_id` необходимо проверить принадлежность заявки, роль субъекта и применимые ограничения на уровне сервера.

**Сценарий контроля:** пользователи А и Б успешно проходят аутентификацию; пользователь А не должен читать заявку пользователя Б, даже зная ее идентификатор. Тест с подстановкой известного идентификатора нужен для проверки бизнес-правила, а не для демонстрации эксплуатационных техник.

## 5. Версионирование интерфейса

Версия файла спецификации (`openapi: 3.1.1`) и версия **самого API** (`info.version: 1.0.0`, префикс `/v1`) — разные понятия. Изменение API фиксируется в журнале совместимости.

| Изменение | Потенциальный эффект | Действие аналитика |
|---|---|---|
| Добавлено необязательное поле ответа | Обычно совместимо с устойчивым клиентом, но требует проверки | Описать поле, обновить примеры |
| Переименовано обязательное поле | Может нарушить клиентов | Запланировать новую версию/переходный период |
| Изменился формат ошибки | Может нарушить обработку отказов | Согласовать договоренность и тесты |
| Изменилось поведение доступа | Риск нарушения безопасности и процесса | Проверить роли и негативные сценарии |

Совместимость зависит не только от JSON-схемы: порядок операций, идемпотентность и семантика кодов ответа также составляют контракт.

## 6. Минимальный набор проверок перед выпуском

1. Спецификация синтаксически валидна и проходит проверку выбранным линтером.
2. Все операции имеют неповторяющиеся `operationId`, описание цели и ожидаемые ответы.
3. Схемы параметров, обязательность полей и ограничения соответствуют реализации.
4. Авторизация проверяется для положительных и отрицательных сценариев.
5. Описаны типовые ошибки: отсутствие доступа, неверные данные, конфликт, недоступность.
6. Примеры не содержат реальных ключей доступа и персональных данных.
7. Согласованы история изменений, версия контракта и поддерживаемые клиентские версии.

## Вывод

Описание API — самостоятельный инженерный артефакт. Его ценность определяется тем, можно ли по контракту разработать клиент, подготовить испытания и установить последствия изменения интерфейса, не прибегая к неформальным уточнениям.

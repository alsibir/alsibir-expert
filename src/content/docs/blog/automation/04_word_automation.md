**Направление:** автоматизация документирования · **Актуализация:** 09.10.2026.

Документ объемом в сотни страниц невозможно надежно проверять только визуальным просмотром. Одни ошибки относятся к языку и содержанию, другие — к структуре файла и могут обнаруживаться программно: неиспользование стилей, разрушенные поля, неверные ссылки, несогласованные подписи и ручные номера заголовков.

## 1. Модель документа, пригодного для проверки

В Microsoft Word документ представляет собой не просто последовательность символов. Он содержит абзацы, стили, поля, закладки, таблицы, разделы, объекты и колонтитулы. Автоматизация должна работать с этими сущностями, а не только искать текстовые совпадения.

| Объект | Что проверяется | Типовая ошибка |
|---|---|---|
| Стиль абзаца | Уровень, имя, параметры | Заголовок сделан жирным вручную |
| Поле `SEQ` | Подписи рисунков и таблиц | Номер рисунка набран текстом |
| Поле `REF` / перекрестная ссылка | Связь с объектом | «Ошибка! Источник ссылки не найден» |
| Закладка | Существование и область действия | Удалена при редактировании |
| Нумерованный список | Привязка к шаблону списка | Номер отделен от абзаца |
| Разрыв раздела | Колонтитул, нумерация страниц | Сброс нумерации после вставки |

## 2. Как организовать проверку

Проверка выполняется на **копии** исходного файла и разделяется на три прохода.

**Проход А — анализ:** собрать статистику стилей, поля с ошибочными результатами, признаки ручной нумерации. В исходнике ничего не менять.

**Проход Б — автоматическая коррекция:** выполнять только однозначные исправления; сохранять журнал изменений и резервную копию.

**Проход В — ручная экспертиза:** проверить ссылки на нормативные документы, технические параметры, подписи и смысловую согласованность. Эти сведения не выводятся из объектной модели Word.

## 3. Пример VBA: безопасный диагностический проход

Макрос ниже **ничего не исправляет**. Он выводит количество абзацев, заголовков со стилями Word и полей, результаты которых содержат характерное сообщение об ошибке. Проверяются основной текст и другие области (`StoryRanges`).

```vb
Option Explicit

Public Sub AuditDocumentStructure()
    Dim doc As Document
    Dim st As Range
    Dim part As Range
    Dim fld As Field
    Dim para As Paragraph
    Dim headingCount As Long
    Dim errorCount As Long
    Dim paraCount As Long

    Set doc = ActiveDocument
    For Each para In doc.Paragraphs
        paraCount = paraCount + 1
        If para.OutlineLevel <> wdOutlineLevelBodyText Then
            headingCount = headingCount + 1
        End If
    Next para

    For Each st In doc.StoryRanges
        Set part = st
        Do While Not part Is Nothing
            For Each fld In part.Fields
                If InStr(1, fld.Result.Text, "Ошибка!", vbTextCompare) > 0 _
                    Or InStr(1, fld.Result.Text, "Error!", vbTextCompare) > 0 Then
                    errorCount = errorCount + 1
                End If
            Next fld
            Set part = part.NextStoryRange
        Loop
    Next st

    MsgBox "Абзацев: " & paraCount & vbCrLf & _
           "Абзацев с уровнем заголовка: " & headingCount & vbCrLf & _
           "Полей с признаком ошибки: " & errorCount, vbInformation
End Sub
```

Такой анализ **не гарантирует** обнаружение всех ошибок полей: сообщения локализованы и могут иметь другую форму, часть проблем проявляется только при пересчете полей, а корректность цели ссылки нужно проверять дополнительно.

## 4. Почему нельзя вслепую обновлять все поля

Метод `Fields.Update` обновляет результаты полей. Однако простой вызов `ActiveDocument.Fields.Update` не обеспечивает универсальную обработку всех областей документа, в частности колонтитулов и иных историй текста. Кроме того, пересчет может изменить номера, ссылки и отображаемые даты. Поэтому перед процедурой требуется сохранять отдельную версию, фиксировать параметры и проводить повторную проверку.

**Пример управляемого сценария:**

```text
Файл до проверки:   Product_PMI_v12.docx
Копия для анализа:  Product_PMI_v12_audit.docx
Отчет:              Product_PMI_v12_audit.md
Файл после правок:  Product_PMI_v13.docx
```

В отчете записываются найденные замечания, выполненные исправления, исключения и результат повторного контроля.

## 5. Практический пример регрессионного дефекта

Исходное состояние:

> «Алгоритм показан на рисунке 12» — номер введен вручную.

После вставки нового рисунка выше по тексту корректная подпись становится «Рисунок 13», но ссылка остается «рисунок 12». **Причина:** текстовая ссылка не связана с объектом подписи. **Коррекция:** создать подпись средствами Word и вставить перекрестную ссылку; при проверке обновить поля на копии и убедиться в правильности целевого объекта.

## 6. Что необходимо проверять дополнительно

- Названия стилей и семантические уровни заголовков.
- Логичность последовательности рисунков, таблиц, приложений и разделов.
- Наличие автоматических подписей, а не только визуально похожих строк.
- Заполнение свойств документа и корректность выходных реквизитов.
- Согласованность текста ТЗ, ПМИ и руководств; несогласованность версий автоматикой Word не устраняется.
- Стабильность документа после экспорта в PDF, включая переносы таблиц и отображение полей.

## Вывод

Качественная автоматизация технического документирования сочетает обработку структурных объектов Word, консервативную стратегию правок и независимую смысловую проверку. Наиболее полезная программа — не та, которая «исправляет все», а та, которая воспроизводимо обнаруживает конкретные классы дефектов и дает отчет о результате.

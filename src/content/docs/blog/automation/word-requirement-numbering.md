## Постановка задачи

Техническое задание может содержать сотни требований, распределённых по разделам и подразделам. При согласовании документа требования перемещаются, уточняются, объединяются и исключаются. Ручная нумерация в этих условиях создаёт риск дублирования идентификаторов, появления неактуальных ссылок и потери трассируемости.

Задача автоматизации состоит не только в присвоении номера, но и в поддержании согласованного состояния документа после структурных изменений. Решение должно обеспечивать регистрацию требования, формирование отображаемого номера, вставку ссылок, обновление зависимостей и проверку целостности.

## Почему стандартных возможностей Word недостаточно

Word поддерживает многоуровневые списки, закладки, поля `REF`, `SEQ`, `STYLEREF` и `HYPERLINK`. Однако эти механизмы решают разные задачи:

| Механизм | Назначение | Ограничение |
|---|---|---|
| Многоуровневая нумерация | Нумерация структурных элементов | Номер меняется при перемещении раздела |
| `SEQ` | Последовательная нумерация элементов | Требует управления последовательностями и обновления полей |
| `REF` | Вывод содержимого или номера объекта по закладке | Результат зависит от диапазона закладки и используемых переключателей |
| `HYPERLINK` | Переход к целевому объекту | Отображаемый текст не пересчитывается автоматически из номера цели |
| Закладка | Адресация диапазона документа | Может быть удалена или повреждена при редактировании |

Важно различать **идентификатор требования** и **его отображаемый номер**. Например, внутренний идентификатор `REQ_000127` может оставаться неизменным, тогда как номер в документе изменяется с `RQ-01` на `RQ-02`. Это разделение позволяет сохранить историю и связи между требованиями.

## Базовый алгоритм: преобразование номера подраздела

Рассматривается сценарий, в котором номер подраздела `4.1` используется для формирования отображаемого обозначения `RQ-01`.

1. Пользователь выбирает заголовок раздела или подраздела.
2. Макрос получает актуальный номер выбранного заголовка через объектную модель Word или корректно настроенную перекрёстную ссылку.
3. Номер преобразуется по заданному правилу. Например, для `4.1` используется последний компонент `1`, дополненный нулём до двух разрядов.
4. К результату добавляется префикс `RQ-`.
5. Создаётся или находится закладка требования, обеспечивающая адресацию.
6. В документ вставляется номер требования или ссылка на него.
7. При изменении структуры документа выполняются пересчёт отображаемых номеров и проверка ссылок.

Правило преобразования необходимо зафиксировать отдельно. Преобразование `4.1 → 01` не является универсальным: для `4.12` результатом может быть `12`, а для `4.1.3` необходимо заранее определить, использовать ли `03`, `01-03` или иную схему.

## Подход с преобразованием REF в HYPERLINK

Один из вариантов реализации предполагает временное использование поля `REF` для получения актуального номера заголовка, а затем замену результата гиперссылкой с подготовленным текстом.

**Создание ссылки:**

1. Определить целевой заголовок и его закладку.
2. Получить номер заголовка средствами Word.
3. Преобразовать номер по установленной маске.
4. Создать `HYPERLINK` с адресом внутри документа и отображаемым текстом `RQ-01`.

**Обновление:**

1. Найти управляемые ссылки на требования.
2. Определить целевую закладку каждой ссылки.
3. Получить актуальный номер целевого заголовка.
4. Сформировать новый отображаемый номер.
5. Обновить текст гиперссылки без потери адреса, форматирования и границ диапазона.

Первоначальная идея предусматривает цикл `HYPERLINK → REF → HYPERLINK`. Такой цикл технически возможен, но не обязателен: если целевая закладка и исходный заголовок известны, номер можно получить непосредственно через объектную модель Word. Это сокращает число операций над полями и снижает риск повреждения документа.

## Предлагаемая архитектура механизма

### 1. Реестр требований

Каждому требованию присваивается постоянный внутренний идентификатор, не зависящий от его позиции в документе. Реестр содержит:

| Атрибут | Пример | Назначение |
|---|---|---|
| Внутренний идентификатор | `REQ_000127` | Неизменяемый ключ требования |
| Закладка | `RQ_REQ_000127` | Адрес требования в Word |
| Отображаемый номер | `RQ-01` | Номер, видимый читателю |
| Источник номера | Заголовок 4.1 | Связь с разделом документа |
| Тип | Функциональное | Классификация требования |
| Статус | Согласовано | Контроль жизненного цикла |
| Контрольные сведения | Версия, дата изменения | Аудит изменений |

Реестр может храниться во внешнем файле либо в пользовательских XML-данных документа. Способ хранения выбирается с учётом требований к переносимости, совместной работе и сопровождению.

### 2. Модуль нумерации

Рекомендуется поддерживать несколько независимых схем:

- **Сквозная:** `RQ-0001`, `RQ-0002`, `RQ-0003`.
- **В пределах раздела:** `RQ-04-001`, `RQ-04-002`.
- **По номеру подраздела:** `RQ-01`, `RQ-02` при привязке к заданной структурной единице.
- **По типу:** `FR-0001`, `NFR-0001`, `IF-0001`.

В настройках следует предусмотреть длину числовой части, набор префиксов, область действия счётчика, правила повторной нумерации и политику обработки удалённых требований.

Ключевое проектное решение: **стабильный идентификатор не должен автоматически изменяться при переносе требования**. Если проект требует перенумерации видимых обозначений, история соответствий старых и новых номеров должна сохраняться.

### 3. Модуль ссылок

Для каждой ссылки необходимо хранить связь с постоянным идентификатором, а не только её видимый текст. При обновлении модуль разрешает идентификатор в актуальный номер и изменяет представление ссылки.

В зависимости от структуры документа возможны два варианта:

- `REF` с переключателем `\h`, когда целевой диапазон и формат результата позволяют получить требуемый текст непосредственно из поля;
- `HYPERLINK` с программно поддерживаемым отображаемым текстом, когда требуется преобразование номера по специальной маске.

Пример кода поля Word:

```text
{ REF RQ_REQ_000127 \h }
{ HYPERLINK \l "RQ_REQ_000127" }
```

Фигурные скобки в примерах обозначают границы полей Word, а не символы, которые достаточно напечатать вручную. Фактическое отображение `REF` определяется содержимым закладки; само по себе поле не превращает `4.1` в `01`.

### 4. Модуль проверки целостности

Проверка документа должна обнаруживать:

- требования без зарегистрированного идентификатора;
- дублирующиеся внутренние идентификаторы и отображаемые номера там, где уникальность обязательна;
- ссылки на отсутствующие закладки;
- закладки, утратившие связь с требованием;
- несоответствие отображаемого номера текущему правилу нумерации;
- нарушенную последовательность номеров;
- ссылки на удалённые или объединённые требования.

Результаты целесообразно представлять в отчёте с типом ошибки, идентификатором требования, местоположением и предлагаемым действием.

## Улучшение пользовательского интерфейса

Вместо перегрузки существующей вкладки «Заголовки» диалога перекрёстных ссылок предлагается отдельная форма с двумя режимами: **«Создать требование»** и **«Вставить ссылку»**.

В режиме создания требования пользователь выбирает источник номера, схему нумерации, префикс и требуемую разрядность. В режиме вставки ссылки доступен поиск по номеру, тексту, типу и статусу требования. Дополнительно следует предусмотреть предварительный просмотр результата и проверку уникальности.

Ограничение количества элементов стандартного комбобокса не следует считать универсальным ограничением Word: вместимость зависит от конкретной реализации интерфейса. Для большого набора префиксов предпочтительны настраиваемый список с прокруткой, поиск или отдельный справочник.

Сочетание `Ctrl+Shift` с выбором заголовка может использоваться как пользовательская команда только при наличии специально реализованного обработчика. Оно не является стандартным способом нумерации требований Word.

## Производительность и безопасность обновления

При большом числе требований нецелесообразно многократно перестраивать все поля документа. Рекомендуется:

1. Один раз построить индекс требований, закладок и ссылок.
2. Выявить изменившиеся заголовки и связанные с ними требования.
3. Пересчитать только затронутые отображаемые номера.
4. Обновить связанные ссылки пакетно.
5. Проверить результаты и сформировать протокол.

Для VBA полезны временное отключение обновления экрана, минимизация обращений к `Selection`, работа с объектами `Range` и восстановление исходных настроек приложения даже при ошибке. Следует учитывать не только основной текст, но и колонтитулы, сноски, текстовые рамки и другие области документа, если там допустимы ссылки на требования.

Перед массовым изменением необходимо создавать резервную копию. Желательно предусмотреть режим предварительной проверки без записи изменений, журнал операций и возможность отката. Время выполнения должно оцениваться измерениями на документах различного объёма, а не предположительными ограничениями по числу полей.

## Пограничные случаи, которые необходимо предусмотреть

| Ситуация | Рекомендуемая обработка |
|---|---|
| Перенос требования из 4.1 в 4.2 | Сохранить внутренний идентификатор, пересчитать отображаемый номер согласно политике проекта |
| Удаление требования | Зафиксировать статус и обнаружить входящие ссылки |
| Копирование абзаца с требованием | Проверить уникальность идентификатора; при создании нового требования выдать новый ключ |
| Изменение уровня заголовка | Проверить соответствие правилам вычисления номера |
| Два требования в одном подразделе | Использовать дополнительный порядковый номер или другую однозначную схему |
| Отсутствие целевой закладки | Не заменять ссылку молча; зарегистрировать ошибку |
| Защищённый документ | Выполнить предварительную проверку возможности редактирования |
| Совместное редактирование | Предусмотреть обнаружение конфликтов и повторную проверку реестра |

## План развития инструмента

**Этап 1. Прототип.** Реализовать регистрацию требования, получение номера заголовка, преобразование номера, создание закладки и вставку ссылки.

**Этап 2. Надёжность.** Добавить стабильные идентификаторы, проверку дубликатов, диагностику повреждённых ссылок и журналирование.

**Этап 3. Массовая обработка.** Реализовать индексирование, пакетное обновление, предварительный просмотр изменений и измерение производительности.

**Этап 4. Трассируемость.** Поддержать атрибуты требований, связи между требованиями, источниками и проверками, а также экспорт матрицы трассируемости.

**Этап 5. Интеграция.** Предусмотреть обмен с внешними системами управления требованиями через согласованный формат данных, например JSON или XML, с сохранением постоянных идентификаторов.

## Критерии приёмки

Работоспособность механизма целесообразно оценивать по проверяемым сценариям:

1. При изменении номера подраздела все связанные отображаемые номера обновляются согласно выбранной схеме.
2. Внутренние идентификаторы остаются неизменными при перемещении требований.
3. Повторный запуск обновления без изменений не меняет документ — обеспечивается идемпотентность.
4. Удалённые закладки и дублирующиеся идентификаторы обнаруживаются и отражаются в отчёте.
5. Ссылки сохраняют переход к правильному требованию после обновления.
6. Массовое обновление не изменяет посторонние гиперссылки и поля.
7. Операции корректно обрабатывают ошибки и не оставляют Word в изменённом служебном состоянии.

Для испытаний необходим набор контрольных документов: небольшой типовой документ, документ с сотнями требований и документ с преднамеренно внесёнными нарушениями.

## Выводы

Автоматизация нумерации требований в Word — задача управления связями и идентичностью объектов документа, а не только форматирования текста. Преобразование `REF → HYPERLINK` представляет собой допустимый частный механизм, но более устойчивое решение строится вокруг постоянного идентификатора требования, централизованного реестра и контролируемого обновления отображаемых номеров.

Такой подход позволяет постепенно превратить Word из средства редактирования текста в инструмент структурированного ведения требований: с проверкой целостности, трассируемостью, управлением изменениями и подготовкой данных для последующей автоматизированной обработки.

## 1. Что такое UX-редактура

**UX-редактура (UX Writing)** — разработка и редактирование текстов пользовательского интерфейса, обеспечивающих понятное, предсказуемое и удобное взаимодействие пользователя с программным продуктом.

В отличие от технического писателя, который преимущественно объясняет, как пользоваться системой, UX-редактор помогает пользователю **выполнять действия непосредственно в интерфейсе, не обращаясь к документации**.

Для специалиста с опытом технического писателя и системного аналитика освоение UX-редактуры предполагает прежде всего переход от описания функциональности к проектированию пользовательского взаимодействия.

### 1.1. Что делает UX-редактор

| Объект редактирования | Задача UX-редактора |
|---|---|
| Названия разделов и меню | Обеспечить понятную навигацию |
| Кнопки | Точно обозначить выполняемое действие |
| Поля ввода | Указать, какие данные необходимо ввести |
| Подсказки | Предупредить ошибки пользователя |
| Сообщения об ошибках | Объяснить причину и способ устранения |
| Уведомления | Сообщить результат выполненного действия |
| Диалоговые окна | Помочь принять обоснованное решение |
| Первоначальная настройка | Объяснить последовательность действий |
| Пустые состояния | Подсказать, как начать работу |
| Подтверждения удаления | Предупредить о последствиях необратимой операции |

Главный критерий качества — не литературная красота текста, а способность пользователя **понять, что происходит, что требуется сделать и какой результат будет получен**.

## 2. Пример UX-редактуры

Пример рассматривается на материале условной системы управления лицензиями программного обеспечения.

### 2.1. Исходный текст интерфейса

**Заголовок:** Операция с файлом

**Описание:** Загрузите соответствующий файл для осуществления процедуры активации функционала.

**Поле:** Укажите файл

**Кнопка:** ОК

### 2.2. Текст после UX-редактуры

**Заголовок:** Активация лицензии

**Описание:** Выберите лицензионный файл `.lic`, полученный от поставщика ПО.

**Поле:** Файл лицензии (`.lic`)

**Кнопка:** Активировать лицензию

Во втором варианте:

- указана цель операции;
- определён необходимый файл;
- исключены избыточные формулировки;
- название кнопки соответствует действию;
- пользователь может понять интерфейс без отдельной инструкции.

Это и есть практический результат UX-редактуры.

## 3. Порядок выполнения UX-редактуры

### Шаг 1. Изучить функциональность

Определить назначение экрана, роль пользователя, доступные операции, обязательные поля и возможные ошибки.

**Исходные материалы:** техническое задание, пользовательские сценарии, прототипы интерфейса, описание API, снимки экранов.

### Шаг 2. Описать пользовательский сценарий

Для каждой операции определить последовательность:

**Цель пользователя → Действие → Результат.**

Для каждой операции дополнительно рассматриваются ошибки, отмена и повторное выполнение.

**Пример:** администратор выбирает файл лицензии, запускает активацию и получает сообщение о результате.

### Шаг 3. Составить реестр интерфейсных текстов

Зафиксировать все заголовки, названия кнопок, поля, подсказки, уведомления и сообщения об ошибках.

Каждому тексту назначить идентификатор, указать экран, контекст и условие отображения.

### Шаг 4. Отредактировать тексты

Применить следующие правила:

- одно действие — одно понятное название;
- короткие предложения вместо сложных конструкций;
- одинаковые термины для одинаковых сущностей;
- название кнопки должно соответствовать её действию;
- сообщения об ошибках должны содержать полезные инструкции;
- технические термины используются только при необходимости.

Эти правила согласуются с распространёнными рекомендациями по проектированию текстов пользовательских интерфейсов, в том числе изложенными в руководствах Microsoft.

### Шаг 5. Проверить все состояния интерфейса

Проверка проводится не только для успешной операции, но и при отсутствии данных, недостаточных правах, неверном формате, сбое соединения и других предусмотренных состояниях.

Особенно важно не подменять диагностическое сообщение общим текстом «Произошла ошибка».

### Шаг 6. Согласовать изменения с разработчиком и аналитиком

Необходимо проверить соответствие текстов реальному поведению системы. Например, нельзя написать «Лицензия активирована», если файл был только загружен, а проверка лицензии ещё не завершилась.

### Шаг 7. Провести проверку на пользователях

Пользователю предлагается выполнить типовую операцию без дополнительных объяснений.

Фиксируются ошибочные действия, затруднения, неоднозначности и случаи обращения к справке.

## 4. Как оформлять результаты работы

Основным рабочим артефактом может быть таблица UX-текстов в Excel, Markdown или системе управления требованиями.

| Идентификатор | Исходный текст | Новый текст | Причина изменения |
|---|---|---|---|
| UI-001 | Осуществить загрузку | Загрузить файл | Устранение канцеляризма |
| UI-002 | Неверный файл | Выберите файл `.lic` | Уточнение требования |
| UI-003 | Успешно | Лицензия активирована | Уточнение результата |
| UI-004 | Ошибка 403 | Недостаточно прав для активации лицензии | Объяснение ограничения |
| UI-005 | Да / Нет | Удалить / Отмена | Конкретизация действий |

В полноценном реестре также рекомендуется предусмотреть поля «Экран», «Роль пользователя», «Условие отображения», «Ограничение по длине», «Статус согласования» и «Комментарий разработчика».

## 5. Как писать сообщения об ошибках

Для большинства ошибок используется логическая схема:

**Что произошло → Почему (если известно) → Что необходимо сделать.**

### 5.1. Неудачное сообщение

> Error 400: Invalid License
>
> ОК

### 5.2. Рекомендуемое сообщение

> **Не удалось активировать лицензию**
>
> Срок действия лицензии истёк. Получите новый лицензионный файл у поставщика ПО.
>
> **Кнопка:** Выбрать другой файл

**Примечание:** Конкретную причину ошибки разрешается указывать только при её достоверном определении системой.

Дополнительно рекомендуется размещать сообщения рядом с проблемными полями, сохранять ранее введённые данные и обеспечивать доступность сообщений для вспомогательных технологий. Подобные правила представлены в GOV.UK Design System.

## 7. Практическое упражнение

### Вопрос 1

Пользователь создаёт новый проект. Как назвать кнопку?

1. Осуществить создание.
2. Создать проект.
3. ОК.

### Вопрос 2

Пользователь не указал обязательное имя проекта. Какое сообщение лучше?

1. Некорректный ввод.
2. Ошибка 1002.
3. Введите название проекта.

### Вопрос 3

Пользователь удаляет проект без возможности восстановления. Что требуется?

1. Кнопка «ОК».
2. Предупреждение о последствиях и явное подтверждение удаления.
3. Только значок корзины.

### Вопрос 4

После нажатия «Сохранить» запрос ещё выполняется. Что показать?

1. «Сохранено».
2. «Сохранение…».
3. «Успешно».

### Ответы и пояснения

| Вопрос | Правильный вариант | Пояснение |
|---|---|---|
| 1 | 2. Создать проект | Название обозначает конкретное действие и объект |
| 2 | 3. Введите название проекта | Текст сообщает, какое действие необходимо выполнить |
| 3 | 2. Предупреждение о последствиях и явное подтверждение удаления | Необратимые действия требуют понятного описания последствий |
| 4 | 2. «Сохранение…» | Сообщение отражает фактическое состояние операции |

## 8. Как связать UX-редактуру с техническим писательством

Наиболее перспективное направление для технического писателя — UX-редактура сложных корпоративных систем: административных панелей, систем лицензирования, программных комплексов, информационных систем государственного и финансового сектора.

В таких продуктах особенно востребованы навыки анализа требований, понимания архитектуры, описания сложных операций и терминологической унификации.

Практический результат работы можно оформить как комплект из четырёх документов:

1. **Аудит интерфейсных текстов** — перечень недостатков и предлагаемых исправлений.
2. **Реестр UX-текстов** — утверждённые формулировки для реализации.
3. **Редакционная политика интерфейса** — правила терминологии, написания команд, ошибок и уведомлений.
4. **Сценарии проверки UX-текстов** — контроль понятности текстов и соответствия поведения интерфейса.

## 9. Вывод

UX-редактура представляет собой самостоятельную область технической коммуникации, тесно связанную с системным анализом. Для её освоения основной акцент следует сделать не на изучении новых правил русского языка, а на анализе пользовательских сценариев, проектировании текстов для различных состояний интерфейса и проверке их эффективности.

Создание программного продукта начинается не с выбора языка программирования, а с понимания задачи. Если заказчик, аналитик, архитектор и разработчики по-разному представляют результат, даже хорошо написанный код может не решить исходную проблему.

Ниже приведена практическая схема запуска ИТ-проекта: какие специалисты требуются, какие решения принимаются до разработки и какие документы должны появиться на каждом этапе. Размер команды может быть любым: в небольшом проекте один человек совмещает несколько ролей, но сами задачи при этом не исчезают.

## С чего начинать новый проект

**Сначала формулируется измеримая цель.** Например, не «улучшить обработку заявок», а «сократить среднее время обработки заявки с десяти до пяти минут без увеличения числа ошибок». Значения в примере условные: в реальном проекте их подтверждают исходными данными.

Рекомендуемый порядок работы:

1. Выяснить, какую бизнес-проблему требуется решить и кто будет пользоваться системой.
2. Описать существующий процесс, его ограничения и критерии успеха.
3. Сформировать функциональные и нефункциональные требования.
4. Согласовать архитектурные решения и границы системы.
5. Разбить работу на небольшие проверяемые результаты.
6. Организовать разработку, испытания, выпуск и сопровождение.

Не стоит переходить к детальному проектированию до согласования ключевых требований. Иначе архитектура будет опираться на предположения, а каждое позднее уточнение способно вызвать переработку.

## Кто за что отвечает

| Роль | Основная задача | Типичный результат |
| --- | --- | --- |
| Заказчик или владелец продукта | Определяет цели, приоритеты, приемлемый результат | Бизнес-цели, критерии приёмки |
| Бизнес-аналитик | Исследует предметную область и бизнес-процессы | Модель процессов, бизнес-требования |
| Системный аналитик | Формализует поведение системы, интерфейсы, данные и ограничения | Спецификация требований, сценарии, контракты интеграции |
| Архитектор | Выбирает принципы построения и интеграции решения | Архитектурные решения, схемы компонентов |
| Руководитель проекта | Согласует сроки, ресурсы, риски и зависимости | План работ, контроль изменений и поставок |
| Разработчик | Реализует и проверяет программные компоненты | Код, модульные тесты, технические пояснения |
| Тестировщик | Проверяет соответствие требованиям и устойчивость работы | Тест-кейсы, протоколы, дефекты |
| Технический писатель | Приводит описания к единой структуре, поддерживает эксплуатационные документы | Руководства, инструкции, справочники, редакционный контроль |

**Роль не равна должности.** Например, руководитель разработки может одновременно выполнять часть архитектурных задач, а системный аналитик — работать с бизнес-требованиями. Однако автоматическое приравнивание системного аналитика к руководителю команды или директору по технологиям приводит к размыванию ответственности.

## Нужен ли руководитель проекта, если есть подробное техническое задание

Наличие технического задания и задач в системе учёта не отменяет управление проектом. Даже при полностью описанной функциональности остаются вопросы доступности специалистов, изменения приоритетов, внешних зависимостей, согласования бюджета и сроков.

В небольшом проекте эти обязанности могут быть переданы владельцу продукта или руководителю разработки. В сложном проекте их следует назначить явно, иначе организационные проблемы начинают решаться разработчиками в ущерб реализации.

## Какие документы действительно нужны

Не требуется создавать максимальное количество документов. Требуется иметь **достаточный набор согласованных и актуальных материалов**, позволяющий разработать, проверить и сопровождать систему.

### До начала разработки

- Краткое описание цели и границ проекта.
- Реестр заинтересованных сторон и ключевых требований.
- Сценарии использования или пользовательские истории с критериями приёмки.
- Перечень интеграций, ограничений и основных рисков.
- Принятые архитектурные решения и открытые вопросы.

### В ходе разработки

- Актуальные контракты API, форматы сообщений и описание моделей данных.
- Решения по архитектуре с объяснением причин выбора.
- Инструкции по развёртыванию тестовой среды и запуску проверок.
- Тестовые сценарии, результаты проверок и журнал изменений.

### Перед передачей заказчику

- Подтверждение выполнения критериев приёмки.
- Инструкции по установке, настройке и эксплуатации.
- Описание резервирования, восстановления и мониторинга, если эти функции предусмотрены системой.
- Перечень известных ограничений и порядок обращения за поддержкой.

Для проектов, где применение ГОСТ является требованием договора или технического задания, дополнительно определяется состав документов по соответствующей системе стандартов. Само наличие ПО не означает автоматической обязанности оформлять каждый документ по ГОСТ 19 или ГОСТ 34.

## Кто должен писать документацию на код и API

Разработчик лучше знает детали реализации: параметры функций, исключения, алгоритмы. Технический писатель отвечает не за угадывание этих деталей, а за понятность и единообразие итогового комплекта.

Эффективный процесс выглядит так:

1. Разработчик обновляет описание поведения компонента вместе с изменением кода.
2. Контракт API и примеры запросов проходят техническую проверку.
3. Технический писатель редактирует структуру, терминологию и сценарии использования.
4. Ответственный специалист подтверждает техническую корректность.
5. Документация публикуется одновременно с соответствующей версией продукта.

Тот же принцип действует для схем баз данных. Не рекомендуется вручную поддерживать вторую несвязанную копию структуры: она быстро расходится с реальной схемой. Лучше связывать описание с миграциями, исходными моделями и процедурами проверки.

## Где хранить документы и изменения

Jira и аналогичные системы подходят для задач и дефектов; Confluence и внутренние порталы — для согласованных описаний; Git — для версионируемых текстовых спецификаций и исходного кода. Конкретное сочетание зависит от инфраструктуры организации.

Важно определить **единый актуальный экземпляр каждого документа**, владельца и порядок согласования. Если два файла с одинаковым названием редактируются независимо, наличие формально правильного ТЗ не предотвращает ошибки.

## Проверка перед началом реализации

Перед передачей задач разработчикам полезно ответить на вопросы:

- Понятно ли, какую бизнес-проблему решает каждый блок функциональности?
- Указаны ли условия, при которых результат считается принятым?
- Определены ли источники данных, интеграции, права доступа и ограничения?
- Выявлены ли вопросы, на которые пока нет ответа?
- Назначен ли ответственный за актуальность каждого документа?

Если на существенные вопросы нельзя ответить, задачу следует уточнить до реализации. Исправление неоднозначного требования на этапе обсуждения обычно проще, чем переработка готового программного компонента.

## Итог

Правильная организация разработки — не жёсткая последовательность должностей, а согласованный процесс принятия решений. Заказчик определяет цель, аналитики описывают потребность и поведение системы, архитектор обеспечивает техническую целостность, разработчики реализуют решение, специалисты по тестированию проверяют результат, а технический писатель помогает сохранить знания в доступной форме.
